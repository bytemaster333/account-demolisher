## External audit

An independent external audit of Account Demolisher has not been performed yet. The app tells you
so: whenever it is on mainnet, from the build default, a restored selection or a switch, the
browser has to acknowledge that the code has not had an independent audit before the app operates
(`src/components/layout/AppShell.tsx`, `src/components/layout/MainnetConfirm.tsx`). A co-signer on
`/sign` signs on the network the signing request names and does not see that notice.

When the external audit runs, its findings and their resolutions are published on this page.

## Internal pre-audit review

Before the external audit, the codebase went through an internal review at commit `764d808`
(2026-10-02):

- Seventeen area reviewers read every line of `src/` (136 files, 32,341 lines), the Docker, CI and
  release configuration, `package.json`, `public/`, every page of this documentation, the root
  markdown, and every file under `tests/` and `scripts/qa/`, recording the exact line ranges read.
- An independent verifier tried to refute each finding against the code and the installed
  library sources, and where possible proved it with a scratch script, a focused test, or a
  read-only testnet or mainnet query. Verifiers also reported issues the reviewers missed.
- A completeness pass compared the coverage against the file tree and sent six further reviewer
  and verifier pairs into cross-cutting areas: the sign-time guards, slippage, fail-open error
  handling, secret and token data flow, concurrency, and drift between discovery and execution.
- 483 raw findings: 479 survived verification and 4 were refuted. They were merged into 259
  distinct issues, one per root cause, and two more found while fixing were added, for 261.
- Nothing was signed or submitted on mainnet during the review.

Each fix was made with a regression test written to fail first, and checked by a separate reviewer
before it was merged.

### Severity scale

| Severity | Meaning                                                                                                             |
| -------- | ------------------------------------------------------------------------------------------------------------------- |
| CRITICAL | Loss or stranding of user funds, key or secret compromise, or signing something the user did not intend             |
| HIGH     | A close fails or misreports for a realistic account, a security control is bypassed, or success is reported falsely |
| MEDIUM   | A real bug with a narrower trigger or recoverable impact, or misleading UI on a money path                          |
| LOW      | An edge case, robustness, minor UX or accessibility                                                                 |
| INFO     | Code quality, dead code, stale comments, or documentation drift with no runtime impact                              |

- **Fixed**: every CRITICAL issue, and 217 in all.
- **Partial**: the fix landed for part of the issue, and a follow-up in another area remains

- **Open**: 25 of the 28 are documentation issues (2 HIGH, 7 MEDIUM, 10 LOW, 6 INFO): pages that

  friendbot-funded specs fully in parallel (LOW).
- **Not a bug**: 4 issues the fix work showed were already handled.

### What the CRITICAL fixes changed

| Issue                                                                                                | Now                                                                                                                                                                 |
| ---------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Allow-listed DeFi steps signed simulation-recorded authorization trees without checking nested calls | Every DeFi step is held to the exact authorization tree its call needs (`src/lib/soroban/defi-auth-guard.ts`)                                                       |
| Retry after a failed forward could report success while the balance sat in the mediator              | A forward that did not land ends `forward_pending`, and Retry runs it                                                                                               |
| A merge whose confirmation was lost could lead Retry to re-mint the mediator and strand the balance  | Submissions are journaled by hash and looked up before anything is signed again; a funded mediator is adopted                                                       |
| The mediator token's 15-minute lifetime could run out before the merge                               | A new flow is minted right before the funding batch, and tokens renew through `/api/mediator/reissue`                                                               |
| Two-pass Soroban builds reused one account object and submitted at the wrong sequence                | Every build gets its own copy of the account at the same sequence, so a probe build never advances the real one                                                     |
| Aquarius discovery failed open when its API and event scan both came back empty                      | A protocol that cannot be read records an error, and the merge guard refuses on it                                                                                  |
| Blend discovery read only the V2 backstop                                                            | Both backstops are read, and V1 pools resolve to the V1 backstop                                                                                                    |
| A shared-account signing request could merge around open Soroban positions                           | A signing request is refused while the plan holds any step besides the classic close, or discovery reported an error, and the bundle is checked again before submit |

## FxDAO

FxDAO was a supported protocol and is no longer, because the protocol shut down on chain. The
evidence, gathered on 2026-10-06:

- The mainnet vaults contract `CCUN4RXU5VNDHSF4S4RKV4ZJYMX2YWKOH6L4AKEKVNVDQ7HY5QIAO4UB` now runs a
  wasm whose interface exports only `evict` and `upgrade`.
- Its `CoreState.panic_mode` is `true`.
- `VaultsInfo` shows `total_vaults = 0` and `total_col = 0` for USD, EUR and GBP.
- The contract's data on stellar.expert holds only the instance entry, so no vault record remains,
  live or archived.
- The six testnet FxDAO contracts the app had pinned no longer exist.

There are no FxDAO positions left to unwind, so the app no longer discovers them or plans exits for
them, and the allow-list carries no FxDAO entries. The FxDAO stablecoins already issued (about
17,504 USD, 3,857 EUR and 3,110 GBP by the debt counters) are ordinary balances: a close sells them
for XLM, returns them to their issuer, or asks you, like any other credit balance.

## Dependency posture

Runtime dependencies are pinned by the committed `pnpm-lock.yaml` and installed with
`--frozen-lockfile`. CI and the release workflow both run `pnpm audit --prod --audit-level high`
and fail on any high or critical advisory in the production tree. The production tree carries none.

One override in `pnpm-workspace.yaml` lifts `axios` to 1.20.0 under the Stellar SDK 16 copy that
`@blend-capital/blend-sdk` pins, which would otherwise ship `axios` 1.18.0 and its advisories.

No advisory is suppressed. `pnpm audit --prod` reports five below the gate, on 2026-10-09. All five
sit under `@hot-wallet/sdk`, which the Stellar Wallets Kit's HOT Wallet module depends on. The app
does not import that module (it is not in the kit's default modules), and none of the five has a
fix inside the version ranges that pull it in:

| --------------------- | ----------------- | -------- | ----------------------------------------------------------------------------- |
| `GHSA-848j-6mx2-7j84` | elliptic 6.6.1    | Low      | No patched release exists. The app signs with ed25519 through the Stellar SDK |
